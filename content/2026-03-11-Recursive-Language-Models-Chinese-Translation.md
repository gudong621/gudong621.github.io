## 摘要

我们通过推理时扩展 (inference-time scaling) 的视角，研究如何让大型语言模型 (LLM) 处理任意长度的提示词。我们提出**递归语言模型 (Recursive Language Models, RLMs)**，这是一种通用推理策略，将长提示词视为外部环境的一部分，允许 LLM 以编程方式检查、分解提示词，并在提示词片段上递归调用自身。我们发现 RLM 能够成功处理比模型上下文窗口大两个数量级的输入，并且即使在较短的提示词上，也在四个不同的长上下文任务中显著优于基础 LLM 和常见的长上下文脚手架的质量，同时每次查询的成本相当 (或更低)。

## 1 引言

尽管推理和工具使用方面进展迅速，现代语言模型仍然有有限的上下文长度，并且即使在这些限制内，似乎不可避免地会出现**上下文腐烂**(context rot) 现象——如图 1 左侧所示，即使是 GPT-5 这样的前沿模型，其质量也会随着上下文变长而快速下降。虽然我们期望通过训练、架构和基础设施的改进，上下文长度会稳步提升，但我们感兴趣的是：能否通过将推理时计算扩展几个数量级，来 dramatically 扩展通用 LLM 的上下文大小？随着 LLM 开始被广泛用于长 horizon 任务（它们必须常规性地处理数千万甚至数亿 token），这变得越来越紧迫。

我们通过推理时计算扩展的视角来研究这个问题。我们从**核外算法**(out-of-core algorithms) 中汲取广泛灵感——在这种系统中，具有小而快的主内存的数据处理系统可以通过巧妙地管理数据如何 fetched 到内存中，来处理大得多的数据集。处理长上下文问题的推理时方法非常常见，但通常是特定于任务的。

一个通用且日益流行的推理时方法是**上下文压缩**(context condensation/compaction)：当上下文超过长度阈值时，反复对其进行摘要。不幸的是，压缩对于需要密集访问提示词多个部分的任务来说很少足够 expressive，因为它实际上假设提示词早期出现的一些细节可以安全地忘记，以便为新内容腾出空间。

### RLM 的核心思想

我们引入**递归语言模型 (RLMs)**，这是一种通用推理范式，用于 dramatically 扩展现代 LLM 的有效输入和输出长度。关键洞察是：**长提示词不应直接馈送到神经网络（如 Transformer）中，而应被视为 LLM 可以符号化交互的环境的一部分**。

如图 2 所示，RLM 暴露出与 LLM 相同的外部接口：它接受任意结构的字符串提示词，并产生字符串响应。给定提示词 P，RLM 初始化一个 Read-Eval-Print Loop (REPL) 编程环境，其中 P 被设置为变量的值。然后它向 LLM 提供关于 REPL 环境的一般上下文（例如字符串 P 的长度），并允许它编写代码来 peek 进和分解 P，并迭代地观察执行产生的任何副作用。**关键的是，RLM 鼓励 LLM 在其生成的代码中，程序化地构造子任务，在这些子任务上可以递归调用自身**。

通过将提示词视为外部环境中的对象，RLM 的这一简单设计解决了先前许多方法的基础性限制——这些方法专注于任务的递归分解，但无法让它们的输入扩展到基础 LLM 的上下文窗口之外。

### 评估结果

我们使用前沿闭源模型 (GPT-5) 和前沿开源模型 (Qwen3-Coder-480B-A35B) 在四个不同任务上评估 RLM，这些任务具有不同程度的复杂性：深度研究、信息聚合、代码库理解，以及一个合成配对推理任务（即使是前沿模型也会在该任务上灾难性失败）。我们将 RLM 与直接 LLM 调用、上下文压缩、检索工具使用 agent 和代码生成 agent 进行比较。

我们发现 RLM 在 10M+ token 规模上表现出极强的性能，并且在长上下文处理方面大幅优于所有其他方法，在大多数情况下以双位数的百分比优势胜出，同时保持相当或更低的成本。特别是，如图 1 所示，RLM 在更长上下文和更复杂任务上表现出远不那么严重的退化。

## 2 扩展长上下文任务

最近的工作成功地论证了 LLM 的有效上下文窗口通常可能比模型的最大物理 token 数短得多。更进一步，我们假设 LLM 的有效上下文窗口不能独立于特定任务来理解。也就是说，更"复杂"的问题会在甚至更短的长度上表现出退化。因此，我们必须根据任务的复杂度如何随提示词长度扩展来表征任务。

例如，needle-in-a-haystack (NIAH) 问题通常在扩展提示词长度时保持"针"不变。因此，虽然前几代模型在 NIAH 任务上挣扎，但前沿模型即使在 1M+ token 设置中也能可靠地在 RULER 中解决这些任务。尽管如此，同样的模型在更短的长度上也会在 OOLONG 上挣扎——这是一个答案显式依赖于提示词中几乎每一行的任务。

### 2.1 任务

基于这一直觉，我们的经验评估围绕以下任务设计：我们不仅能够改变提示词的长度，还能考虑不同的问题复杂度扩展模式。我们根据**信息密度**松散地表征每个任务，即 agent 需要处理多少信息来回答任务，以及这如何随不同输入大小扩展。

**S-NIAH**: 遵循 RULER 中的单 needle-in-the-haystack 任务，我们考虑 50 个单针寻址任务，需要在大量不相关文本中找到特定短语或数字。这些任务无论输入大小如何都只需要找到一个答案，因此相对于输入长度，处理成本大致呈常数扩展。

**BrowseComp-Plus (1K documents)**: 一个用于 DeepResearch 问题的多跳问答基准，需要对多个不同文档进行推理。该基准提供 100K 文档的验证离线语料库，保证包含每个任务的金标、证据和硬负样本文档。我们使用 150 个随机采样任务作为评估集；我们向模型或 agent 提供 1000 个随机选择的文档，其中保证金标和证据文档存在。我们报告正确答案的百分比。每个任务的答案需要将几个文档的信息拼凑在一起，这使得这些任务比 S-NIAH 更复杂，尽管也只需要常数数量的文档来回答。

**OOLONG**: 一个长推理基准，需要语义地检查和转换输入块，然后聚合这些块形成最终答案。我们基于原始论文报告评分，数值答案评分为 score(ŷ)=0.75^|y-ŷ|，其他答案为精确匹配。我们专门关注 trec_coarse 拆分，这是一组 50 个任务，针对带有语义标签的问题数据集。每个任务需要使用数据集的几乎所有条目，因此相对于输入长度，处理成本呈线性扩展。

**OOLONG-Pairs**: 我们手动修改 OOLONG 的 trec_coarse 拆分，包含 20 个新查询，这些查询专门需要聚合块对来构造最终答案。我们在附录 E.1 中明确提供该基准中的所有查询。我们报告答案的 F1 分数。每个任务需要使用数据集的几乎所有条目对，因此相对于输入长度，处理成本呈二次扩展。

**LongBench-v2 CodeQA**: 来自 LongBench-v2 的多选代码库理解拆分，对现代前沿模型具有挑战性。我们报告为正确答案的百分比。每个任务需要推理代码库中的固定数量文件以找到正确答案。

### 2.2 方法和基线

我们将 RLM 与其他常用的任务无关方法进行比较。对于以下每种方法，我们使用两个当代 LM：GPT-5 (中等推理) 和 Qwen3-Coder-480B-A35B。

**RLM with REPL**: 我们实现一个 RLM，将其上下文作为字符串加载到 Python REPL 环境的内存中。REPL 环境还加载一个模块，允许它在环境中查询子 LM。系统提示词在所有实验中固定（见附录 D）。对于 GPT-5 实验，我们对递归 LM 使用 GPT-5-mini，对根 LM 使用 GPT-5，因为我们发现这一选择在 RLM 的能力和递归调用的成本之间取得了强大的权衡。

**RLM with REPL, no sub-calls**: 我们提供我们方法的消融。在其中，REPL 环境加载上下文，但不能使用子 LM 调用。在这种设置中，LM 仍然可以在 REPL 环境中与其上下文交互，然后提供最终答案。

**Summary agent**: 遵循先前的工作，我们考虑一个迭代 agent，它在上下文被填充时调用上下文摘要。例如，给定文档语料库，它将迭代地查看文档并在满时摘要。在提供的上下文超过模型窗口的情况下，agent 会将输入分块以适应模型上下文窗口，并在这些块上调用相同策略。

**CodeAct (+ BM25)**: 我们直接与 CodeAct agent 比较，该 agent 可以在 ReAct 循环内执行代码。与 RLM 不同，它不将其提示词卸载到代码环境，而是直接提供给 LM。此外，我们为该 agent 配备 BM25 检索器，在适当的情况下索引输入上下文。

## 3 结果和讨论

我们将主要实验集中在表 1 中的基准测试上。此外，我们在图 1 中探索前沿模型和 RLM 性能如何随着输入上下文增长而退化。

**表 1**: 不同方法在 varying 复杂度的长上下文基准上的性能比较。灰色显示每个方法在每个任务上的平均 API 成本±标准差。∗表示方法遇到输入上下文限制的运行。

### 发现 1: RLM 可以扩展到 10M+ token 级别，并且在长上下文任务上优于基础 LM 和现有任务无关 agent 脚手架

在所有任务上，RLM 在远超前沿 LM 有效上下文窗口的输入任务上表现出强劲性能，在保持相当或更便宜的平均 token 成本的同时，性能比基础模型和常见长上下文脚手架高出 up to 2×。值得注意的是，RLM 很好地扩展到扩展基础模型上下文窗口的理论成本——在 BrowseComp-Plus (1K) 上，GPT-5-mini 摄取 6-11M 输入 token 的成本为$1.50-$2.75，而 RLM(GPT-5) 的平均成本为$0.99，并且在所有任务上比摘要和检索基线高出超过 29%。

此外，在处理成本随输入上下文扩展的任务上，RLM 在适合模型上下文窗口的任务上比基础模型有显著改进。在 OOLONG 上，使用 GPT-5 和 Qwen3-Coder 的 RLM 分别比基础模型高出 28.4% 和 33.3%。在 OOLONG-Pairs 上，GPT-5 和 Qwen3-Coder 都几乎没有进展，F1 分数 << 0.1%，而使用这些模型的 RLM 分别达到 58.00% 和 23.11% 的 F1 分数，凸显了 RLM 处理极度信息密集任务的涌现能力。

### 发现 2: REPL 环境对于处理长输入是必要的，而 RLM 的递归子调用在信息密集输入上提供强大收益

RLM 的一个关键特征是将上下文卸载到环境 E 中的变量，模型可以与之交互。即使没有子调用能力，我们的 RLM 消融也能够扩展到模型的上下文限制之外，并在大多数长上下文设置中优于基础模型和其他任务无关基线。在 CodeQA 和 BrowseComp+ 任务上，使用 Qwen3-Coder 的这种消融分别比 RLM 高出 17.9% 和 3%。

在像 OOLONG 或 OOLONG-Pairs 这样的信息密集任务上，我们观察到几种情况，其中递归 LM 子调用是必要的。在§3.1 中，我们看到 RLM(Qwen3-Coder) 通过递归子调用逐行执行必要的语义转换，而没有子调用的消融被迫使用关键词启发式来解决这些任务。在所有信息密集任务上，RLM 比没有子调用的消融高出 10%-59%。

### 发现 3: LM 性能随输入长度和问题复杂度退化，而 RLM 性能扩展更好

基准测试 S-NIAH、OOLONG 和 OOLONG-Pairs 包含固定数量的任务，上下文长度范围从 2^13 到 2^18。此外，每个基准可以根据输入上下文相对于长度的不同处理成本松散分类（大致为常数、线性和二次）。在图 1 中，我们直接比较使用 GPT-5 的 RLM 与基础 GPT-5 在每个任务上——我们发现 GPT-5 性能在更复杂任务上退化显著更快，而 RLM 性能也退化，但速率慢得多。对于超过 2^14 的上下文长度，RLM 持续优于 GPT-5。

此外，RLM 成本与任务复杂度成比例扩展，同时仍然保持与 GPT-5 相同数量级的成本。在§3.1 中，我们探索 RLM 在这些设置中做出的哪些选择导致这些成本差异。最后，在这种设置中，我们还观察到基础 LM 在小输入上下文机制上优于 RLM。通过构造，RLM 比 LM 严格具有更多的表示容量：调用根 LM 的环境选择等价于基础 LM；然而在实践中，我们观察到 RLM 在较小输入长度上性能略差，表明何时使用基础 LM 和何时使用 RLM 之间存在权衡点。

### 发现 4: RLM 的推理成本与基础模型调用相当，但由于轨迹长度差异而方差高

RLM 迭代地与其上下文交互，直到找到合适的答案，导致迭代长度根据任务复杂度有很大差异。在图 3 中，我们绘制了表 1 中所有实验（不包括 BrowseComp-Plus (1K)）的每种方法的四分位数成本。对于 GPT-5，中位数 RLM 运行比中位数基础模型运行更便宜，但许多异常值 RLM 运行比任何基础模型查询都贵得多。然而，与摄取整个输入上下文的摘要基线相比，RLM 便宜 up to 3×，同时在所有任务上保持更强的性能，因为模型能够选择性地查看上下文。

### 发现 5: RLM 是模型无关的推理策略，但不同模型在上下文管理和子调用上表现出不同的整体决策

虽然 GPT-5 和 Qwen3-Coder-480B 都作为 RLM 相对于其基础模型和其他基线表现出强劲性能，但它们也在所有任务上表现出不同的性能和行为。特别是在 BrowseComp-Plus 上，RLM(GPT-5) 几乎解决了所有任务，而 RLM(Qwen3-Coder) 难以解决一半。

我们注意到 RLM 系统提示词在每个模型的所有实验中是固定的，没有为任何特定基准调整。在 GPT-5 和 Qwen3-Coder 之间，提示词的唯一区别是 RLM(Qwen3-Coder) 提示词中额外一行警告不要使用太多子调用（见附录 D）。我们在示例 B.3 中提供这种差异的显式示例，其中 RLM(Qwen3-Coder) 在 OOLONG 中作为单独的子 LM 调用逐行执行语义转换，而 GPT-5 对子查询 LM 保守。

### 3.1 RLM 轨迹中的涌现模式

即使没有显式训练，RLM 也表现出有趣的上下文管理和问题分解行为。我们选择几个 RLM 轨迹片段示例来理解它们如何解决长上下文问题以及它们可以改进的地方。

**基于模型先验使用代码执行过滤输入信息**: RLM 抽象能够在巨大输入上保持强劲性能而不爆炸成本的一个关键直觉是 LM 能够过滤输入上下文而无需显式查看它。此外，模型先验使 RLM 能够缩小搜索空间并处理更少的输入 token。作为一个示例，在图 4a 中，我们观察到 RLM(GPT-5) 使用正则查询搜索包含关键词（如"festival"）和它有关于的短语（如"La Union"）的块。在大多数轨迹中，我们观察到的常见策略是通过打印几行回到根 LM 来探测上下文，然后基于其观察进行过滤。

**分块和递归子调用 LM**: RLM 将本质上无界长度的推理链延迟到子-(R)LM 调用。分解的选择可能极大地影响任务性能，特别是对于信息密集问题。在我们的实验中，我们没有观察到超出均匀分块或关键词搜索的复杂分区策略。在图 4b 中，RLM(Qwen3-Coder) 在 OOLONG 的 1000+ 行上下文中按换行符分块。

**通过小子上下文子 LM 调用进行答案验证**: 我们观察到 RLM 通过子 LM 调用进行答案验证的几个实例。其中一些策略通过使用子 LM 执行验证隐式避免上下文腐烂（见示例 B.1），而其他策略仅使用代码执行来程序化地验证答案是否正确。然而，在某些情况下，答案验证是冗余的，并显著增加每个任务的成本——在示例 B.3 中，我们观察到 OOLONG 上的一个轨迹，模型试图重复其正确答案超过五次，最后选择不正确的答案。

**通过变量传递递归 LM 输出用于长输出任务**: RLM 能够通过返回 REPL 中的变量作为输出来产生本质上无界的 token，远超基础 LM 的限制。通过 REPL，RLM 可以迭代地构造这些变量，作为程序化和子-(R)LM 调用输出的混合。我们在 OOLONG-Pairs 轨迹中大量观察到这种策略，其中 RLM 将子 LM 调用在输入上的输出存储在变量中，并将它们缝合在一起形成最终答案（见图 4c）。

## 4 相关工作

**长上下文 LM 系统**: 长上下文管理主要有两个正交方向：1) 直接改变基础 LM 的架构并重新训练以处理更长上下文，2) 在 LM 周围构建隐式处理上下文的脚手架——RLM 专注于后者。一类流行的策略是**有损上下文管理**，使用摘要或截断来压缩输入上下文，但可能丢失细粒度信息。例如，MemWalker 构建输入的树状数据结构，LM 可以在回答长上下文问题时导航。ReSum 是另一项工作，为多轮 agent 添加摘要工具以定期压缩上下文。另一类策略在 agent 脚手架中实现显式内存层次结构。RLM 与先前工作的不同之处在于所有上下文窗口管理由 LM 自己隐式处理。

**通过子 LM 调用进行任务分解**: 许多基于 LM 的 agent 使用多个精心放置的 LM 调用来解决问题，但这些调用基于人工工程的工作流放置。几种方法如 ViperGPT、THREAD、DisCIPL、ReDel、Context Folding 和 AgentFold 探索将子 LM 调用的选择延迟给 LM。这些技术强调通过递归 LM 调用进行任务分解，但无法处理超出基础 LM 长度的长上下文输入。RLM 则通过一个极其简单的直觉（即将提示词作为外部环境的一部分）来实现，以符号化地操作任意长的字符串，并通过来自持久 REPL 环境的执行反馈迭代地细化其递归。

## 5 局限性和未来工作

虽然 RLM 在现有 LM 的上下文窗口限制之外的任务上表现出强劲性能，且推理成本合理，但实现 RLM 的最优机制仍未被充分探索。我们专注于 Python REPL 环境内的同步子调用，但我们注意到涉及异步子调用和沙盒 REPL 的替代策略可能显著降低 RLM 的运行时间和推理成本。此外，我们选择使用最大递归深度为 1（即子调用是 LM）；虽然我们在现有长上下文基准上发现了强劲性能，但我们认为未来工作应该调查更深层的递归。

最后，我们专注于使用现有前沿模型评估 RLM。显式训练模型作为 RLM 使用（例如作为根或子 LM）可能提供额外的性能改进——正如我们在§3.1 中发现的，当前模型在其上下文上是低效的决策者。我们假设 RLM 轨迹可以被视为一种推理形式，可以通过自举现有前沿模型来训练。

---

## 6 结论

我们引入了递归语言模型 (RLM)，这是一种用于语言模型的通用推理框架，它卸载输入上下文，并使语言模型能够在提供输出之前递归地子查询语言模型。我们探索了该框架的一个实例，它将上下文作为内存中的变量卸载到 Python REPL 环境中，使 LM 能够在代码和递归 LM 调用中推理其上下文，而不是纯粹在 token 空间中推理。我们在多种设置和模型上的结果表明，RLM 是长上下文问题和通用推理的有效任务无关范式。我们很高兴看到未来工作显式训练模型作为 RLM 推理，这可能导致下一代语言模型系统的另一个扩展轴。
