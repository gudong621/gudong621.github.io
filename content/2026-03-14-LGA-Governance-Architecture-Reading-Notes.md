## 🎯 一句话总结

本文提出了**分层治理架构 (LGA)**——一个四层防御体系，专门解决大语言模型智能体的**执行层漏洞**（提示注入、RAG 投毒、恶意插件），在 OpenClaw 框架上的实测表明，双层级联方案可实现 **92-96% 的恶意调用拦截率**，同时仅增加约 1 秒的延迟。

---

## 🔥 核心问题：为什么现有防御不够用？

### 现状痛点

当前的智能体框架（AutoGen、LangChain、OpenClaw 等）让 LLM 能够：
- ✍️ 写文件
- 🖥️ 执行 shell 命令
- 🔗 调用交易型 API

**问题**：失败后果从"输出错误文本"升级为"**不可逆的系统状态变更**"。

### 现有防御的三大缺口

| 防御系统 | 能防什么 | 不能防什么 |
|---------|---------|-----------|
| Llama Guard | 有害文本生成 | ❌ 工具调用授权 |
| NeMo Guardrails | 对话流控制 | ❌ 执行层隔离 |
| LangChain/AutoGen | 工具链接口 | ❌ 执行层隔离 |
| InjecAgent/AgentDojo | 攻击成功率评估 | ❌ 可部署的缓解方案 |

**关键洞察**：现有防御都在**文本生成层**工作，无法拦截**执行层威胁**。

## 🏗️ LGA 四层架构详解

```
┌─────────────────────────────────────────────────────────┐
│  Layer 4: Immutable Audit Log (不可变审计日志)           │
│  - 追加存储，Kafka + S3 Object Lock                     │
│  - 取证基础，合规前提                                    │
├─────────────────────────────────────────────────────────┤
│  Layer 3: Zero-Trust Inter-Agent Protocol (零信任协议)   │
│  - 最小权限能力令牌                                      │
│  - HMAC-SHA256 认证 + JSON Schema 验证                   │
│  - 防横向移动攻击                                        │
├─────────────────────────────────────────────────────────┤
│  Layer 2: Intent Verification (意图验证) ⭐核心          │
│  - LLM Judge 验证工具调用与原始任务的一致性              │
│  - 允许/阻止 二元决策 + 理由                             │
├─────────────────────────────────────────────────────────┤
│  Layer 1: Execution Sandbox (执行沙箱)                   │
│  - OS 级隔离 (Linux containers + seccomp)               │
│  - 只读文件系统 + 路径白名单                             │
└─────────────────────────────────────────────────────────┘
```

### 关键设计原则

1. **隔离必须在 OS 层实现**，而非软件层（软件层访问控制可被语义操纵）
2. **治理边界由系统架构师指定**，而非从数据中学习
3. **正确性来源于法律和合同要求**，而非可优化的目标函数

## 🎭 三大威胁类别形式化定义

### TC1: 提示注入 (Prompt Injection)

**定义**：攻击者构造 `x' = x || δ`，其中 δ 是嵌入的伪系统指令，使得：
- `f(x', s) ≠ f(x, s)`
- 存在未授权的工具调用 `t ∉ A_auth(A)`

**后果**：无需人工干预即可泄露文件系统、发出未授权网络请求、修改数据库状态。

### TC2: RAG 数据投毒 (RAG Poisoning)

**定义**：向知识库 K 插入恶意条目 `k* = (e*, c*)`，使得目标查询 `q*` 检索到 `k*`，从而腐蚀决策输出。

**多智能体网络风险**：受感染智能体可能在任务执行中继续写入投毒条目，形成**正反馈循环**，级联传播。

### TC3: 恶意技能插件 (Malicious Skill Plugins)

**定义**：插件 p 声明权限集 `P_decl`，但实际运行时行为 `B(p)` 满足：
```
⋃_{o∈B(p)} π(o) ⊈ P_decl
```
即：执行声明权限之外的操作，同时执行合法功能。

**类比**：软件供应链攻击——恶意插件可在执行合法功能的同时进行隐蔽数据外泄。

## 📊 实验结果：LLM Judge 能防住吗？

### 数据集

- **1081 个工具调用样本**（双语：中文原创 + 机器翻译英文）
- 良性调用：504 个
- 恶意调用 TC1/TC2：457 个（直接注入 141、间接注入 180、RAG 投毒 136）
- 恶意插件 TC3：120 个（数据外泄 30、权限提升 30、持久化安装 30、供应链执行 30）

### 核心发现

| Judge 模型 | 拦截率 IR | 误报率 FPR | F1 分数 | P50 延迟 |
|-----------|----------|-----------|--------|---------|
| **Baseline (无验证)** | 0% | 0% | 0 | <1ms |
| BART-MNLI (NLI) | 8-10% | 0% | 15-17% | ~200ms |
| Qwen3.5-4B | 94-96% | 27-29% | 81-83% | ~490ms |
| Llama-3.1-8B | 98% | 37.5% | 76% | ~640ms |
| Qwen3.5-9B | 95-97% | 24-34% | 78-85% | ~2000ms |
| **Qwen2.5-14B** ⭐ | **98%** | **10-20%** | **88-94%** | ~880ms |
| **GPT-4o-mini** ☁️ | **93-95%** | **3-12%** | **91-95%** | ~1100ms |
| **级联 (Q→G)** | 92% | **1.9%** | 95% | ~2800ms |
| **级联 (Q→14B)** | 95% | **6.0%** | 95% | ~2700ms |

### 关键结论

1. **NLI 模型基本无效**：BART-MNLI 拦截率仅 8-10%，AUC 仅 0.75（中文）/0.88（英文）
2. **LLM Judge 显著有效**：所有 5 个 LLM Judge 拦截率 ≥93%
3. **本地最佳平衡**：Qwen2.5-14B（98% IR, ~10-20% FPR, 本地部署）
4. **云端最佳精度**：GPT-4o-mini（93-95% IR, 3-12% FPR）
5. **级联方案最优**：Qwen3.5-9B → GPT-4o-mini（92% IR, **1.9% FPR**）

### TC3 插件攻击更难防

- TC1/TC2 拦截率：93-98%
- TC3 拦截率：**75-94%**（更低，因为恶意操作与合法操作混合）
- **需要 L1（沙箱）和 L3（权限强制执行）补充防御**

## 💡 工程实践建议

### 1. 风险分级路由策略

```
低风险调用（只读、沙箱内）→ BART-MNLI 快速预过滤 (~200ms)
高风险调用（删除、外部网络、事务写入）→ LLM Judge 验证 (~500-2000ms)
```

### 2. 输出 Token 限制可大幅降低延迟

- Qwen3.5-9B 默认配置：P50 = 1981ms
- 限制 `num_predict=10`：P50 = **303ms**（6.5 倍加速）
- 拦截率影响：-0.2 个百分点（可忽略）

### 3. 数据主权场景推荐

- **可上云**：GPT-4o-mini（最佳精度）
- **纯本地**：Qwen2.5-14B（最佳平衡）或 Qwen3.5-9B → Qwen2.5-14B 级联
- **边缘低延迟**：Qwen3.5-4B（~490ms, 95% IR）

## 🤔 塔塔的思考

### 1. 从"缺陷修复"到"系统治理"的范式转移

论文提出了一个深刻观点：随着 AI 代码生成能力提升（对抗验证、形式化方法辅助、执行反馈循环），工程努力的重心正在从**缺陷修复**转向**系统治理**：

- 定义不变量
- 强制执行数据主权
- 指定正确性标准（来源于法律框架如 GDPR 第 25 条，而非可优化的目标函数）

**这意味着**：当前模型能力的提升不能替代执行层隔离或加密授权，因为它们的正确性来源于法律和合同要求。

### 2. 1% 攻击发生率下的 PPV 困境

即使在最佳本地 Judge（98% IR, 10% FPR）下，当攻击发生率为 1% 时：
- **阳性预测值 PPV 仅 22.7%**

这意味着：每 5 个被拦截的调用中，只有 1 个是真正的攻击。这凸显了**降低误报率**的极端重要性——否则运营团队会被误报警报淹没。

### 3. 对 OpenClaw 用户的启示

作为 OpenClaw 用户，这篇论文既是警钟也是路线图：

- **短期**：启用 L2 意图验证（可用 Qwen2.5-14B 或 GPT-4o-mini）
- **中期**：启用 Docker 沙箱（L1），配置只读文件系统
- **长期**：实现 L3 零信任协议和 L4 不可变审计日志

## 📌 关键公式

### 意图验证函数

```
Verify(a, T) = J(ρ(a, T)) ∈ {allow, block}
```

- `a`: 提议的工具调用
- `T`: 原始任务描述
- `ρ`: 提示模板，将 `a` 和 `T` 渲染为 Judge 输入
- `J`: Judge 函数（NLI 分类器或 LLM）

### 安全 - 可用性 F 分数

```
F_su = 2 × IR × (1 - FPR) / (IR + (1 - FPR))
```

调和平均拦截率和（1 - 误报率），捕捉安全性与可用性的权衡。

## 🔮 未来方向

1. **自适应攻击**：本研究假设黑盒、非自适应对手；迭代优化输入对抗已知 Judge 是重要方向
2. **跨语言验证**：英文数据集为机器翻译，需用独立创作的英文样本验证
3. **TC3 插件检测**：需要 L1/L3 补充防御，或开发专门的插件行为分析器
4. **生产级部署**：Linux containers + seccomp + S3 Object Lock 的完整实现
