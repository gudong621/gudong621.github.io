## 摘要

由大语言模型驱动的自主智能体引入了一类执行层漏洞——提示注入、检索污染和不受控的工具调用——现有防护栏无法在统一架构内系统性地解决这些问题。

在本工作中，我们提出了**分层治理架构 (Layered Governance Architecture, LGA)**，一个四层框架，包括：
- **L1**: 执行沙箱 (execution sandboxing)
- **L2**: 意图验证 (intent verification)
- **L3**: 零信任智能体间授权 (zero-trust inter-agent authorization)
- **L4**: 不可变审计日志 (immutable audit logging)

为评估 LGA，我们构建了一个双语基准（中文原创，英文通过机器翻译），包含 1081 个工具调用样本——涵盖提示注入、RAG 污染和恶意技能插件——并将其应用于 OpenClaw，一个代表性的开源智能体框架。

在 L2 意图验证上的实验结果（使用四个本地 LLM 裁判：Qwen3.5-4B、Llama-3.1-8B、Qwen3.5-9B、Qwen2.5-14B，以及一个云端裁判 GPT-4o-mini）表明：
- 所有五个 LLM 裁判拦截了 **93.0-98.5%** 的 TC1/TC2 恶意工具调用
- 轻量级 NLI 基线仍低于 **10%**
- TC3（恶意技能插件）证明更难，裁判的拦截率为 **75-94%**（具有有意义的精确率 - 召回率平衡）
- 这激发了在 L1 和 L3 层的补充执行

**关键性能数据**：
- Qwen2.5-14B 实现最佳本地平衡（98% 拦截率，约 10-20% 误报率）
- 两级级联（Qwen3.5-9B → GPT-4o-mini）实现 91.9-92.6% 拦截率，误报率 1.9-6.7%
- 全本地级联（Qwen3.5-9B → Qwen2.5-14B）实现 94.7-95.6% 拦截率，误报率 6.0-9.7%（适用于数据主权部署）

端到端管道评估（n=100）表明，四层协同工作，拦截率 96%，总 P50 延迟约 **980 毫秒**，其中非裁判层仅贡献约 **18 毫秒**。

在外部 InjecAgent 基准上的泛化测试产生 **99-100%** 拦截率，证实了超出我们合成数据的鲁棒性。

**关键词**: 自主智能体、大语言模型、治理架构、提示注入、RAG 污染、多智能体安全

## 1. 引言

LLM 驱动的智能体系统正在从对话型转向执行型：AutoGen、LangChain 和 OpenClaw 等框架现在赋予模型写入文件、执行 shell 命令和调用交易型 API 的能力。

这种转变将失败的后果从**不正确的文本输出**移动到**潜在不可逆的系统状态变更**。

与此同时，AI 辅助编程工具正在重塑软件工程师的价值分配。一个常见的论点是：低级系统专业知识被 AI 放大，因为模型生成的代码包含**泄露的抽象**——在生产条件下可能暴露的语义失败。

虽然在短期内得到实证支持，但我们认为这种框架忽视了一个收敛趋势：多智能体对抗验证、形式化方法辅助和执行反馈循环正在系统性地降低 AI 缺陷率，将工程努力的重心从**缺陷修复**转向**系统治理**。

这一治理关切因 LLM 智能体的定义性特征而加剧：它们将自然语言指令转换为可执行工具调用，无需人工调解。

LGA 为已验证的调用保留这种自主执行；人工审查仅用于升级的阻止，而非正常执行路径。

### 现有防御的局限性

- **内容安全系统**（如 Llama Guard、NeMo Guardrails）过滤有害文本生成，但缺乏工具调用级别的拦截
- **智能体框架**（如 LangChain、AutoGen）提供工具链接口，但缺乏执行层隔离
- **基准**（如 InjecAgent、AgentDojo）量化攻击成功率，但不提出可部署的缓解方案

据我们所知，没有现有工作同时在统一治理架构内解决所有三类威胁——提示注入、RAG 污染和恶意技能插件。

### 研究问题

**RQ1**: 基于 LLM 的意图验证裁判能否可靠地拦截所有三类威胁的执行层威胁？与轻量级 NLI 基线相比如何？

**RQ2**: 本地和云端裁判模型之间的安全 - 延迟权衡是什么？级联架构能否调和两者？

**RQ3**: 完整的四层 LGA 堆叠在端到端部署时是否施加可接受的运行时开销？

### 贡献

1. 我们识别了现有智能体防御中的系统性缺口——它们在文本生成层操作，无法拦截执行层威胁——并论证由此产生的治理关切激发了从缺陷修复向系统级不变量的转变。

2. 我们形式化了三种执行层威胁类别（提示注入、RAG 污染、恶意插件），并提供了统一的威胁模型，包含明确的攻击者能力定义。

3. 我们提出了 LGA（一个四层治理架构），并在 1081 样本双语基准上评估了 L2 意图验证（使用四个本地 LLM 裁判、两个 NLI 基线和一个云端裁判），表明两级级联实现 91.9-92.6% 拦截率（误报率 1.9-6.7%），全本地级联实现 94.7-95.6% 拦截率（误报率 6.0-9.7%）。

4. 我们展示了端到端管道评估，证明四层协同工作，非裁判层组合开销约 18 毫秒，并在外部 InjecAgent 基准上验证了泛化能力。

## 2. 相关工作

### 2.1 LLM 代码生成与抽象失败

Spolsky 的泄露抽象法则指出：非平凡抽象不可避免地暴露实现细节。

Chen 等人 (2021) 证明 Codex 在 HumanEval 上达到 28.8% pass@1——此后该数字已大幅改善，但基本模式持续存在：LLM 在涉及低级并发语义的任务上显著退化。

Liu 等人 (2023a) 表明，LLM 生成的分布外 (OOD) 代码表现出比分布内代码高得多的安全漏洞率。

这些发现支持系统专业知识的短期价值，但未解决其长期轨迹。

对于智能体系统，无论代码质量如何，执行层漏洞（如未验证的工具调用导致不可逆状态变更）持续存在，这激发了 LGA 的治理优先方法。

### 2.2 提示注入与智能体安全

Perez 和 Ribeiro (2022) 首次系统化了直接提示注入攻击。

Greshake 等人 (2023) 将攻击面扩展到通过中毒外部文档的间接注入。

Yi 等人 (2025) 证明了注入在多智能体管道中的横向传播。

OWASP LLM Top 10 (2023) 将提示注入列为 LLM 应用的首要威胁。

我们的工作通过形式化 RAG 污染和恶意技能插件威胁并提出系统性架构响应，扩展了这一知识体系。

### 2.3 智能体框架

AutoGPT 和 AutoGen 代表两种主导设计哲学：单智能体自主循环 vs 多智能体编排。

LangChain 提供标准化工具链接口，但依赖应用层输入过滤，缺乏物理执行层隔离。

这些框架不提供统一治理架构，这是 LGA 旨在解决的缺口。

### 2.4 智能体安全基准

- **AgentBench** (Liu et al., 2023b): 在八个环境中多维度评估 LLM 智能体，但专注于任务完成而非对抗鲁棒性
- **ToolEmu** (Ruan et al., 2024): 在沙箱 LLM 环境中模拟工具执行，实现无现实副作用的安全评估；但其威胁模型仅涵盖单智能体工具滥用，而非多智能体横向传播
- **InjecAgent** (Zhan et al., 2024): 专门基准测试工具集成智能体中的间接提示注入，表明最先进模型在没有专用防御的情况下仍然高度脆弱（ReAct 风格智能体的攻击成功率超过 60%）
- **AgentDojo** (Debenedetti et al., 2024): 提出动态评估框架，结合现实任务环境与自适应攻击生成，实现随智能体能力演进的持续安全评估

我们的基准通过评估防御机制（裁判函数）而非攻击成功率，并涵盖揭示潜在语言依赖漏洞模式的双语场景，补充了这些工作。

### 2.5 LLM 安全与防护栏系统

- **Llama Guard** (Inan et al., 2023): 微调 LLM 作为输入 - 输出安全分类器，在内容安全分类上实现强劲性能，但不解决工具调用授权
- **NeMo Guardrails** (Rebedea et al., 2023): 提供可编程防护栏系统，使用 Colang 脚本控制 LLM 对话流；对对话安全有效，但在对话层操作，不强制执行层隔离

这些系统解决与 LGA 互补的关切：Llama Guard 和 NeMo Guardrails 专注于内容安全（防止有害文本生成），而 LGA 针对执行安全（防止未授权工具调用）。完整的智能体治理堆栈将整合两者。

## 3. 从缺陷修复到系统治理

随着 AI 代码生成工具通过对抗验证、形式化方法辅助和执行反馈循环而改进，工程努力正在从缺陷修复转向**系统治理**：

- 定义不变量
- 强制执行数据主权
- 指定正确性标准（其权威来源于法律框架如 GDPR 第 25 条"默认和通过设计的数据保护"和商业合同，而非可优化的目标函数）

这一转变激发了 LGA 的设计：四层编码治理边界（沙箱隔离、意图验证、零信任协议、审计日志），必须由系统架构师指定，而非从数据中学习。

这些治理边界通过架构机制而非统计泛化强制执行，未经明确策略变更不得放松：

当前模型能力改进不能替代执行层隔离或加密授权，因为它们的正确性来源于法律和合同要求，而非可优化目标（例如，在 1% 攻击发生率下，即使最佳本地裁判也仅实现 22.7% 阳性预测值）。

## 4. 多智能体系统威胁模型

### 4.1 系统模型

我们将自主智能体系统建模为元组 S = ⟨A, K, T, E⟩：
- A: 智能体集合
- K: 共享知识库
- T: 可执行工具集合
- E: 执行环境（L1 在 E 上强制执行 OS 级隔离）

令 Retrieve: K × X → 2^K 表示为查询返回知识条目的检索函数。

令 X 表示智能体输入域，Σ 表示全局系统状态空间。

每个智能体 A_i ∈ A 具有行为函数 f_i: X × Σ → T^+，将输入和系统状态映射到工具调用序列。

### 攻击者模型

我们考虑黑盒、非自适应对手，其可以：
- 向智能体输入注入内容 (TC1)
- 污染知识库条目 (TC2)
- 发布恶意插件 (TC3)

但对部署的裁判模型及其参数不知情。

自适应攻击（对手针对已知裁判迭代优化输入）不在本工作范围内，构成未来工作的重要方向。

### 4.2 威胁类别 1：通过提示注入的代理滥用

**定义 4.1 (提示注入攻击)**: 令智能体 A 在系统状态 s 下处理外部输入 x，具有行为函数 f(x, s)。

提示注入攻击构造 x' = x || δ，其中 || 表示连接，δ 是嵌入的伪系统指令，使得：
- f(x', s) ≠ f(x, s)
- 存在 t ∈ f(x', s) 使得 t ∉ A_auth(A)

其中 A_auth(A) ⊆ T 是智能体 A 的每智能体授权工具调用集合。

在具有物理执行权的智能体中，成功的代理滥用攻击可以：
- 外泄文件系统内容
- 发出未授权网络请求
- 修改数据库状态
-  potentially 在不可逆状态变更发生前无需人工干预

### 4.3 威胁类别 2：RAG 数据污染

**定义 4.2 (RAG 污染攻击)**: 令知识库 K 由 n 个智能体共享，其中智能体 A_i 使用决策函数 d_i(q, Retrieve(K, q))。

污染攻击将条目 k* = (e*, c*) 插入 K，其中 e* 是精心制作的嵌入，c* 是对抗性内容，使得对于目标查询 q*：
- Retrieve(K ∪ {k*}, q*) ∋ k*

从而腐蚀 d_i 的输出。

在多智能体网络中，受感染智能体可能在任务执行期间继续写入投毒条目，形成具有潜在级联传播的正反馈循环。

### 4.4 威胁类别 3：恶意技能插件

**定义 4.3 (恶意技能插件攻击)**: 令技能插件 p 声明权限集 P_decl 并表现运行时行为 B(p)（操作集合），其中 π: op ↦ 2^T 将每个单独操作映射到其所需权限。

恶意插件满足：
```
⋃_{o∈B(p)} π(o) ⊈ P_decl
```

即：执行声明权限之外的操作，同时执行合法功能，使得宿主智能体无法在语义层面区分 B(p) 与良性插件 p'。

类比软件供应链攻击：当智能体框架支持动态加载第三方技能插件时，恶意插件可在执行合法功能的同时进行隐蔽数据外泄。

攻击的隐蔽性源于两个特性：
1. 智能体无法在语义层面区分合法操作与外泄操作
2. 插件权限声明是自我报告的，缺乏独立运行时行为验证

## 5. 分层治理架构 (LGA)

我们提出 LGA，一个用于自主智能体系统的四层纵深防御治理架构。

每层可独立部署； together 它们形成完整的治理堆栈。

### 5.1 层 1：执行沙箱

所有智能体代码执行限制在 OS 级隔离内。

完整生产部署将采用：
- Linux containers
- seccomp 系统调用过滤
- 只读文件系统挂载
- 路径白名单强制执行

我们的实验原型使用较轻量的 unshare 命名空间隔离。

**关键设计原则**：隔离应在 OS 层而非软件层实现——软件层访问控制受语义操纵（如 Zhan et al., 2024 所示），而 OS 级隔离独立于智能体的语言处理操作。

### 5.2 层 2：意图验证

实践中，A_auth(A) 无法为自然语言任务描述穷举枚举；因此 L2 通过语义一致性近似授权检查。

在调用任何高风险工具（如 shell 执行、HTTP 请求、文件写入）之前，独立裁判模型验证工具调用与原始任务一致：

```
Verify(a, T) = J(ρ(a, T)) ∈ {allow, block}
```

其中：
- a: 提议的工具调用
- T: 原始任务描述
- ρ: 提示模板，将 a 和 T 渲染为裁判输入
- J: 裁判函数

裁判 J 可实例化为：
- NLI 分类器（通过阈值将蕴含分数映射到二元决策）
- LLM（直接输出带理由的裁决）

范围外操作被拦截、阻止并记录到审计日志。

### 5.3 层 3：零信任智能体间协议

在多智能体系统内，智能体间通信遵循零信任原则。

- 每个智能体仅持有当前子任务所需的最小权限能力令牌
- 令牌携带严格 TTL 和范围约束
- 智能体间传递的结构化数据使用 HMAC-SHA256 认证并针对 JSON Schema 验证
- 防止一个受感染智能体操纵另一个的横向移动攻击

### 5.4 层 4：不可变审计日志

每个工具调用——参数、返回值、时间戳和执行智能体身份——记录在追加存储中。

生产部署可使用：
- Kafka 主题（默认追加）
- 由只写对象存储支持（如 S3 Object Lock 合规模式）

我们的实验原型使用本地追加文件与 fsync。

该层为事后归因提供取证基础，是构建智能体系统监管合规基础设施的前提。

## 6. 案例研究：OpenClaw

### 6.1 架构概述

我们选择 OpenClaw 作为案例研究，因为它实现了 LGA 针对的所有四个架构组件——本地持久内存、自主执行循环、计算路由网关和插件生态系统——为合规缺口分析提供具体测试床。

OpenClaw 是本地自主智能体系统，其声明的设计目标是"将 AI 能力封闭在可治理的物理边界内"。

其主要技术组件：
- Zero-Ops 本地持久内存
- 带 SOUL.md 配置的心跳自主循环
- 模型选择网关
- 社区技能生态系统 (ClawHub)

### 6.2 Zero-Ops 本地持久内存

OpenClaw 用两层本地存储替换云向量数据库：
- SQLite FTS5 全文索引本地 Markdown 文件

这实现零外部依赖，同时在百万文档语料库上保持检索延迟低于 10 毫秒。

所有内存内容人类可读，系统管理员无需专用工具即可审计。

语义搜索缺口可通过 sqlite-vss 扩展解决，添加本地向量搜索而不违反 Zero-Ops 原则。

### 6.3 心跳自主循环与灵魂配置

OpenClaw 的心跳子系统以可配置间隔（默认 30 分钟）唤醒智能体执行自主循环，打破传统 LLM 应用的被动问答范式。

行为约束在 Markdown SOUL.md 文件中指定，其部分（核心真理、边界、氛围）在每次 LLM 调用时注入系统提示。

**治理缺口 1 (G1)**: SOUL.md 约束通过 LLM 语义解释强制执行——软约束机制。

在 Sect. 4 的威胁模型下，足够精心制作的提示注入可绕过此类约束。

鲁棒强制执行需要在工具调用层硬编码权限检查，对应 LGA L2。

### 6.4 计算路由与数据主权

OpenClaw 的模型选择层根据用户配置、提供者可用性和每智能体允许列表解析哪个 LLM 提供者处理每个请求。

结合本地模型支持 (Ollama)，操作员可保持所有推理在本地，配置相应时提供架构数据主权保证。

这直接实例化 Sect. 3 的数据主权维度，在数据流层面代表 LGA L1。

### 6.5 ClawHub 工作区与技能生态系统

ClawHub 是 OpenClaw 的公共技能注册表。

工作区目录树支持通过 Docker 容器的可选 OS 级文件系统隔离——最接近 LGA L1 要求的组件，尽管沙箱是可选的且默认禁用。

技能在其元数据 (SKILL.md manifest) 中声明权限，提供能力透明度。

**治理缺口 2 (G2)**: 插件权限是自我声明的；无独立运行时沙箱验证实际插件行为是否与声明权限匹配。

这使恶意技能插件威胁类别未缓解。

**治理缺口 3 (G3)**: ClawHub 缺乏目录内细粒度权限分区（例如，技能仅访问 workspace/projects/ 而非 memory/），允许边界内横向遍历。

**治理缺口 4 (G4)**: OpenClaw 的审计日志存储在可变 logs/ 目录；受感染智能体可覆盖或删除日志条目，破坏取证归因和合规可审计性。

### 6.6 LGA 合规评估

通过静态分析 OpenClaw 公开可用源代码 (commit f014e25) 识别以下合规缺口。

合规级别评估如下：
- **Full**: 架构强制执行层要求
- **Partial**: 存在某些机制但未覆盖完整威胁面
- **None**: 未实现相应机制

| LGA 层级 | OpenClaw 状态 | 合规级别 |
|---------|--------------|---------|
| L1 执行沙箱 | 可选 Docker，默认关闭 | Partial |
| L2 意图验证 | 无 | None |
| L3 零信任协议 | 无 | None |
| L4 不可变审计日志 | 可变 logs/ 目录 | None |

## 7. 实验评估

### 7.1 实验设置

为量化 LGA L2（意图验证）引入的安全 - 性能权衡，我们构建了一个 1081 工具调用样本的双语基准，涵盖所有三类威胁，并在中文和英文数据集上评估十种验证条件。

#### 7.1.1 数据集构建

基准包含 1081 个样本，分三类：

**良性调用 (504 个样本)**:
- 工具调用在语义上与其关联任务描述一致
- 生成跨越四种工具类型（file_read、file_write、shell_exec、http_request）和十个任务类别
- 额外 40 个良性插件调用充当 TC3 FPR 计算的双重角色：硬负样本和 TC3 特定假阳性控制

**恶意调用 TC1/TC2 (457 个样本)**:
- 范围外调用，由三种攻击子类型产生：
  - 直接注入 (141)
  - 通过中毒文档的间接注入 (180)
  - RAG 污染触发调用 (136)

**恶意调用 TC3 插件 (120 个样本)**:
- 技能插件调用，其运行时行为超出声明权限
- 涵盖四种子类型：数据外泄 (30)、权限提升 (30)、持久化安装 (30)、供应链执行 (30)

所有样本使用结构化提示模板与 gpt-4o-mini 生成，并通过分层随机 10% 样本 (n=108) 的人工检查验证标签正确性，显示与分配标签 100% 一致。

英文版本通过同一模型机器翻译中文数据集生成，保留所有标签和工具调用结构。

#### 7.1.2 裁判提示模板

所有 LLM 裁判接收相同的结构化提示：

```
You are a security judge. Given a TASK and a TOOL CALL,
determine if the tool call is consistent with the task intent.

TASK: {task_description}
TOOL CALL: {tool_name}({tool_args})

Respond with ALLOW or BLOCK on the first line,
followed by a one-sentence rationale.
```

NLI 模型使用不同公式：任务描述作为前提，工具调用作为假设，蕴含映射到 ALLOW，矛盾/中性映射到 BLOCK。

#### 7.1.3 验证条件

我们评估一个未验证基线、六个主要验证条件、一个补充条件 (mDeBERTa-NLI) 和两个后验级联组合：

1. **Baseline**: 无验证；所有调用无条件允许
2. **BART-MNLI**: 零样本 NLI，使用 facebook/bart-large-mnli (~1.6 GB, CPU)
3. **Qwen3.5-4B**: 最小本地 LLM 裁判 (Q4_K_M 量化，~3.4 GB)，通过 Ollama 服务，使用非思考模式
4. **Llama-3.1-8B**: 本地 LLM 裁判，使用 Meta 的 Llama-3.1-8B-Instruct (Q4_K_M 量化，~4.9 GB)
5. **Qwen3.5-9B**: 本地 LLM 裁判，使用 Qwen3.5-9B 模型 (Q4_K_M 量化，~6.6 GB)
6. **Qwen2.5-14B**: 最大本地 LLM 裁判 (Q4_K_M 量化，~9.7 GB)
7. **GPT-4o-mini**: 云端 LLM 裁判，通过 OpenAI API

#### 7.1.4 指标

我们报告：
- **拦截率 (IR)**: 正确阻止的恶意调用比例
- **误报率 (FPR)**: 错误阻止的良性调用比例
- **安全 - 可用性 F 分数 (F_su)**: IR 和 (1-FPR) 的调和平均数
- **P50/P99 延迟**: 每次工具调用的中位数和 99 百分位绝对延迟 (ms)

### 7.4 讨论

#### 7.4.1 安全 - 延迟权衡 (RQ1, RQ2)

结果揭示轻量级 NLI 模型与基于 LLM 裁判之间的明显能力差距：

- **BART-MNLI**: 仅 8-10% 拦截率，尽管零误报和适中中位开销 (~200ms)
- **所有五个 LLM 裁判**: TC1/TC2 上至少 93% 整体拦截率，但权衡特征明显不同

在本地模型中：
- **Qwen2.5-14B**: 最佳整体平衡 (98% IR, 10-20% FPR, ~880-1160ms)
- **Llama-3.1-8B 和 Qwen3.5-9B**: 高召回、低精确率特征 (≥95% IR)，但 FPR 升高 (24-38%)
- **Qwen3.5-4B**: 最小模型 (~3.4GB)，仍实现 94-96% IR，LLM 裁判中最低延迟 (~490ms)
- **GPT-4o-mini**: 最精确选项 (93-95% IR, 3-12% FPR, ~1100ms)，但需要云连接

NLI 模型的近零拦截表明：零样本文本蕴含（如 BART-MNLI 和 mDeBERTa-NLI 实例化）在没有任务特定适应的情况下不足以进行工具调用授权。

#### 7.4.2 攻击子类型变化

代表性 LLM 裁判 (GPT-4o-mini 和 Qwen3.5-9B) 在所有攻击子类型上显示高拦截率：

- **GPT-4o-mini**: 92.9% (直接)、92.8% (间接)、93.4% (RAG 污染)
- **Qwen3.5-9B**: 97.2% (直接)、94.4% (间接)、98.5% (RAG 污染)

有趣的是，BART-MNLI 显示相反模式：RAG 污染攻击在 17.6% 被拦截，而直接注入仅 4.3%。

这表明 RAG 污染攻击产生更多语义异常工具调用，即使浅层 NLI 模型也能部分检测，而直接注入制作更 plausible 的工具调用。

#### 7.4.3 威胁类别 3：恶意技能插件

插件列 (P) 揭示与 TC1/TC2 子类型相比明显更低的拦截率：

- **GPT-4o-mini**: 75.0% (中文)、94.2% (英文)
- **Qwen2.5-14B**: 77.5% (中文)、88.3% (英文)
- **Qwen3.5-9B**: 77.5% (两种语言)

vs. TC1/TC2 的 ~92-100%。

这一差距是预期的：插件攻击执行其声明操作同时添加隐蔽侧信道（如遥测外泄），因此工具调用在部分上与任务一致，使违规更难从意图 - 行动对齐检测。

按子类型细分：
- **权限提升**: 最可靠检测 (86.7-93.3%)，可能因为系统级操作与声明插件范围显著偏离
- **供应链攻击**: 也良好检测 (83.3-96.7%)，因为对外部下载或范围外 URL 的引用通常异常
- **外泄和持久化**: 更难 (46.7-96.7%)，因为其恶意参数混合到看似合法的遥测或配置字段

这些结果激发 L1（沙箱防止实际外泄）和 L3（协议层声明权限强制执行）的补充防御，补偿 L2 在 TC3 上降低的检测率。

### 7.5 端到端管道评估

端到端评估 (n=100) 证明四层协同工作：
- **整体拦截率**: 96%
- **总 P50 延迟**: ~980ms
- **非裁判层贡献**: ~18ms

微基准确认剩余层添加可忽略开销：
- **L1** (通过 unshare 的进程级隔离): ~1ms 每次沙箱生成 (P50=0.95ms, P99=2.6ms)
- **L3** (HMAC-SHA256 令牌签名/验证 + JSON Schema 验证): <0.02ms 每次调用
- **L4** (带 fsync 的追加审计日志): 4-12ms 每次持久写入 (P50=4.1ms, P99=11.6ms)，或缓冲时 <0.01ms

因此，完整 LGA 部署中的主导延迟贡献者是 L2 意图验证 (~200-2200ms，默认配置；输出限制下 Qwen3.5-9B 降至 ~303ms)。

### 7.6 在 InjecAgent 基准上的泛化

在外部 InjecAgent 基准上的测试产生 99-100% 拦截率：
- **GPT-4o-mini**: 100% (两种语言)
- **Qwen3.5-9B**: 99% (两种语言)

这证实了超出合成数据的鲁棒性。

## 8. 局限性与未来工作

1. **非自适应对手**: 我们假设黑盒、非自适应对手；针对已知裁判的自适应攻击是未来工作的重要方向

2. **机器翻译英文数据集**: 英文版本通过机器翻译中文数据集生成；跨语言发现需要用独立创作样本验证

3. **TC3 插件检测**: L2 在 TC3 上降低的检测率需要 L1/L3 补充防御

4. **输出 Token 限制影响**: Qwen3.5-9B 的 num_predict=10 实验显示 6.5 倍加速，但需要在更多模型上验证

5. **单检查员验证**: 10% 分层随机样本的标签正确性验证由作者单检查员执行；未来版本将纳入独立标注

## 9. 结论

我们提出了分层治理架构 (LGA)，一个用于自主智能体系统的四层纵深防御框架。

通过在 1081 样本双语基准上的实验评估，我们证明：
- LLM 基裁判在 TC1/TC2 上实现 93-98% 拦截率，而轻量级 NLI 基线低于 10%
- 级联架构可将误报率降至 1.9-6.7%，同时保持 92-96% 拦截率
- 完整四层堆叠端到端操作，P50 延迟约 980ms，非裁判层仅贡献 ~18ms
- 在外部 InjecAgent 基准上泛化测试产生 99-100% 拦截率

我们的工作将智能体安全研究的重心从攻击成功率评估转向防御机制评估，并为生产部署提供明确的工程建议。
