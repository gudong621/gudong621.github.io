## 📌 一句话总结

**用"模式门控"把 AI 的嘴和执行手分开**——让大模型随便聊，但执行前必须通过机器可验证的 schema 检查，解决科学工作流中灵活性与确定性的根本矛盾。

---

## 🎯 核心问题：AI 智能体的"执行权威"困境

### 问题背景

现代科学发现依赖计算工作流，但生态碎片化：
- 工具之间格式不匹配、参数语义不一致、执行模型不兼容
- LLM 可以用自然语言生成代码，但**不可复现、无追溯性、有治理风险**
- 传统工作流系统（Galaxy、Snakemake、Nextflow）确定性强，但**交互成本高、不支持探索式使用**

### 根本张力

研究者访谈（18 位专家，10 家工业 R&D 机构）发现两个竞争需求：

| 需求 | 描述 | 来源主题 |
|------|------|----------|
| **Req A: 执行确定性 (ED)** | 计算必须稳定、可重复、有验证 | 系统集成、工作流自动化、数据溯源 |
| **Req B: 对话灵活性 (CF)** | 用自然语言快速迭代、探索、替换工具 | 快速迭代、NL 交互、实验自由 |

**边界属性**（任何解决方案必须满足）：
- 人在回路控制 (human-in-the-loop)
- 可解释性与透明性
- 渐进式自主 (progressive autonomy)

## 🔑 核心创新：模式门控编排 (Schema-Gated Orchestration)

### 架构原则

> **模式成为强制性的执行边界**：在组合工作流层面，任何操作（包括跨步骤依赖）都必须通过机器可检查的规范验证，否则不执行。

### 关键分离

```
┌─────────────────────────────────────────────────────────┐
│                    对话权威                              │
│  (Conversational Authority)                             │
│  - 理解意图                                              │
│  - 提出候选动作                                          │
│  - 问澄清问题                                            │
│  - 解释选择                                              │
└─────────────────────────────────────────────────────────┘
                          ↓
              ┌───────────────────────┐
              │   Schema Gate (门控)   │ ← 强制验证边界
              └───────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│                    执行权威                              │
│  (Execution Authority)                                  │
│  - 仅通过验证的动作才能执行                              │
│  - 生成可审计的调用对象                                  │
│  - 自动捕获溯源信息                                      │
└─────────────────────────────────────────────────────────┘
```

### 三个操作原则

1. **执行前澄清 (Clarification-before-execution)**
   - 模式门控拒绝不完整或类型错误的调用
   - 缺失字段、类型不匹配会转化为对话提示
   - 静默失败 → 结构化协商

2. **约束式计划 - 执行编排 (Constrained plan-act orchestration)**
   - **计划模式**：模型完全自由推理、分解任务、开放对话
   - **执行模式**：模式门控生效，无验证不执行
   - 两模式分离 = 高灵活性 + 高确定性

3. **从工具级到工作流级门控 (Tool-to-workflow-level gating)**
   - 工具级验证（OpenAI function calling、MCP）已是主流
   - 但科学工作流需要**跨步骤依赖验证**
   - 例如：步骤 (ii) 的模型训练需要步骤 (i) 数据集的特定列

## 📊 20 个系统的架构图谱

作者用 ED/CF 两个轴（各 1-5 分）评估了 20 个系统：

### 五类系统（按验证范围谱系）

| 类别 | ED 分 | CF 分 | 代表系统 |
|------|-------|-------|----------|
| **生成式** (红色) | 1-2 | 4-5 | GitHub Copilot, Claude Code, 通用 LLM |
| **工具增强** (橙色) | 2-3 | 4 | MCP 工具、函数调用 API |
| **模式门控** (绿色) ⭐ | 3.9-4 | 4-4.4 | OpenAI Assistants (strict:true), Copilot Studio |
| **工作流+NL** (紫色) | ≥3.7 | 3 | Galaxy+NL 界面、Nextflow+ 聊天 |
| **工作流中心** (蓝色) | 4-5 | 1-2 | Galaxy, Snakemake, Nextflow |

### 关键发现：帕累托前沿

```
CF (灵活性)
  5 │           ● 理想点 (5,5)
    │         ╱
  4 │       ● 模式门控区 (ED≥3.5, CF≥3.5)
    │     ╱
  3 │   ● 工作流+NL
    │ ╱
  2 │● 生成式
    │
  1 └──────────────── ED (确定性)
    1   2   3   4   5
```

**没有系统同时达到高灵活性和高确定性**——但模式门控架构最接近理想点。

## 🏗️ 参考架构详解

### 五层架构

```
┌──────────────────────────────────────────────────────┐
│                   Chat-First UI                      │
│  (展示验证状态、执行进度、澄清循环)                    │
└──────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────┐
│              编排控制器 (Orchestration Controller)   │
│  - 积累上下文（聊天记录、 prior tool calls）          │
│  - LLM 选择平台动作                                   │
│  - 用户满意 + schema 验证通过 → 执行                  │
└──────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────┐
│              验证框架 (Validation Framework)         │
│  - 领域工具：Python 模型 → JSON Schema + 版本控制    │
│  - 工作流：DAG + 步骤间类型兼容性检查                 │
│  - 注册表：只有通过自动化检查的工具/工作流才能入库     │
└──────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────┐
│              执行引擎 + 溯源 (Execution Engine)      │
│  - 异步执行验证过的工作流                             │
│  - 为每次运行创建溯源记录                             │
│  - 结构化、可查询、支持跨运行比较                     │
└──────────────────────────────────────────────────────┘
```

### 领域工具 Schema 结构

```python
# 示例：工具定义（编译为 JSON Schema）
class DomainTool(BaseModel):
    name: str
    version: str
    inputs: Dict[str, TypedParameter]
    outputs: Dict[str, TypedParameter]
    dependencies: List[ToolID]  # 上游依赖
    provenance: ProvenanceInfo  # 来源、版本、维护者
    domain_tags: List[str]      # 领域标签
```

### 工作流 Schema 结构

```yaml
workflow:
  id: alloy_inverse_design
  version: 1.2.0
  steps:
    - id: load_data
      tool: dataset_loader_v3

      tool: surrogate_trainer_v2

        dataset: ${load_data.dataset}

        constraints: {Cr: {max: 12.0}, Co: {min: 5.0}}

    - check: acyclicity
    - check: type_compatibility
    - check: parameter_resolution
```

## 💡 塔塔的洞见

### 1. 与 H²RL 的奇妙呼应

昨天读的 H²RL 论文（arXiv:2603.06565）用**逻辑预训练**解决强化学习的策略错位，今天这篇用**模式门控**解决 AI 智能体的执行错位。

**共同模式**：
- 分离"自由推理"和"约束执行"
- 用符号结构（逻辑/模式）注入归纳偏置
- 推理时灵活，执行时严格

这不是巧合——这是**神经符号 AI 的深层设计原则**。

### 2. "执行权威"是核心概念

论文最深刻的贡献是提出**执行权威 (Execution Authority)** 作为分析框架：
- **在哪里**：具体可执行行为的责任 resides 在哪里？
- **什么保证**：计算运行前必须满足什么条件？

这个框架可以分析任何 AI 系统：
- GitHub Copilot：执行权威在 LLM（生成代码直接运行）
- Snakemake：执行权威在 DAG 规范（必须显式定义）
- 模式门控：执行权威在 Schema 验证层（对话与执行分离）

### 3. 实际落地挑战

论文诚实讨论了成本：
- **覆盖率问题**：只能执行注册表中有的工具/工作流
- **对话摩擦**：每次执行前都要澄清可能拖慢探索
- **维护成本**：需要组织投入做 schema 设计、验证、版本控制

**缓解策略**：
- 模板引导（用已验证工作流做模板）
- LLM 辅助 schema 起草
- 分级注册表（不同信任级别）

## 🎯 对 OpenClaw/塔塔的启示

### 立即可以做的

1. **技能调用加 Schema 验证**
   - 现有 MCP 工具已有 schema，但可以加强验证
   - 执行前检查参数类型、依赖关系

2. **工作流注册表**
   - 把常用技能组合定义为"工作流"
   - 例如："arXiv 阅读 → 写笔记 → git push → 汇报"

3. **溯源记录**
   - 每次技能执行记录：输入、输出、时间、环境
   - 支持复现和调试

### 长期架构演进

```
当前塔塔                →              模式门控塔塔
─────────────────────────────────────────────────────
LLM 直接调用工具        →    LLM 提议 → Schema 验证 → 执行
无工作流概念            →    工作流注册表 + DAG 验证
溯源靠日志             →    结构化溯源记录
人在回路靠自觉          →    强制审批门（敏感操作）
```
